# What limits each backend

The CenterNet-style detector with 380,631 (onnx.json › params) parameters, batch 1, 192 px,
`hard/val`, one shared x86 laptop. Every number below is followed by the tracked file and
key it comes from (`runs/<file> › key/path`); `python edge/test_notes.py` checks each one.
Timings move between sessions on this laptop (last section): compare rows inside one file only.

| Backend | Measured | What limits it |
|---|---|---|
| PyTorch eager fp32 | 1 thread 5.14 ms (onnx.json › latency_ms/torch_eager_1t), 4 threads 2.54 ms (onnx.json › latency_ms/torch_eager_4t), 8 threads 2.75 ms (onnx.json › latency_ms/torch_eager_8t) | The runtime, not the arithmetic: the same graph in ONNX Runtime takes 3.69 ms (onnx.json › latency_ms/onnxrt_1t) on 1 thread at the same mAP 0.9127 (onnx.json › mAP_onnx). More than 4 threads is slower. |
| ONNX Runtime fp32 | 1 thread 3.57 ms (quant_minmax.json › ref/latency_ms/1t), 4 threads 1.52 ms (quant_minmax.json › ref/latency_ms/4t) | Thread scaling flattens: 4 to 8 threads goes 1.12 ms (onnx.json › latency_ms/onnxrt_4t) to 1.01 ms (onnx.json › latency_ms/onnxrt_8t). Why (not profiled): batch 1 at 192 px leaves little work per layer to split; ORT profiling would show it. |
| ONNX Runtime INT8 static (QDQ) | 1 thread 1.38 ms (quant_minmax.json › latency_ms/1t), 4 threads 0.61 ms (quant_minmax.json › latency_ms/4t); mAP 0.9097 (quant_minmax.json › score/mAP) vs 0.9107 (quant_minmax.json › ref/score/mAP) | Exact reproducibility, not speed: the heatmap sits on few levels, so 144 (cpp_ort.json › images_with_tie_at_k) of 200 images tie at the 10th score and top-k order is not unique; a second implementation needs a tie rule to match. Calibrated on 200 (quant_minmax.json › calib_images) sim images only; on the real HOPE photos it scores 0.0061 (real_hope_onnx.json › models/detector_int8_minmax.onnx/mAP) vs fp32 0.0063 (real_hope_onnx.json › models/detector.onnx/mAP), so calibration adds no real-photo loss (the photos fail anyway, see README). |
| ONNX Runtime INT8 dynamic | 1 thread 1.82 ms (quant_dynamic.json › latency_ms/1t), 4 threads 1.54 ms (quant_dynamic.json › latency_ms/4t) | Barely scales with threads, while static INT8 does. The graph has 15 (quant_dynamic.json › nodes/ConvInteger) ConvInteger and 115 (quant_dynamic.json › nodes/total) nodes against 92 (quant_minmax.json › nodes/total) for static: activations are quantised inside the graph on every call ([ONNX Runtime quantization docs](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)). Profiled on 1 thread, that work is visible: ConvInteger 1.3388 ms (op_profile.json › graphs/detector_int8_dynamic.onnx/by_op_ms/ConvInteger) plus DynamicQuantizeLinear 0.2131 ms (op_profile.json › graphs/detector_int8_dynamic.onnx/by_op_ms/DynamicQuantizeLinear), Mul 0.1160 ms (op_profile.json › graphs/detector_int8_dynamic.onnx/by_op_ms/Mul), Add 0.1068 ms (op_profile.json › graphs/detector_int8_dynamic.onnx/by_op_ms/Add) and Cast 0.0639 ms (op_profile.json › graphs/detector_int8_dynamic.onnx/by_op_ms/Cast) per image; the static graph spends 0.0441 ms (op_profile.json › graphs/detector_int8_minmax.onnx/by_op_ms/QuantizeLinear) on QuantizeLinear and runs its convolutions in 1.0384 ms (op_profile.json › graphs/detector_int8_minmax.onnx/by_op_ms/QLinearConv). Profiled at 4 threads (`--threads 4`; a repeat run agrees within 0.08 ms per op; the profiler adds its own cost, so compare ops, not totals): ConvInteger 1.2562 ms (op_profile_4t.json › graphs/detector_int8_dynamic.onnx/by_op_ms/ConvInteger) against 1.3388 ms (op_profile.json › graphs/detector_int8_dynamic.onnx/by_op_ms/ConvInteger) on 1 thread, so the integer convolution kernel gains almost nothing from the extra threads, while static QLinearConv falls to 0.5583 ms (op_profile_4t.json › graphs/detector_int8_minmax.onnx/by_op_ms/QLinearConv); the element-wise rescale ops get slower, Cast 0.2533 ms (op_profile_4t.json › graphs/detector_int8_dynamic.onnx/by_op_ms/Cast), Mul 0.1912 ms (op_profile_4t.json › graphs/detector_int8_dynamic.onnx/by_op_ms/Mul). |
| Pruned 50 % channels, ORT fp32 | 1 thread 2.42 ms (prune_50.json › latency_ms/onnxrt_1t); mAP 0.8454 (prune_50.json › score/mAP) | Latency does not follow compute: MACs drop from 214,990,848 (prune_50.json › macs_base) to 101,795,328 (prune_50.json › macs), time only from 3.57 to 2.42 ms. Profiled on 1 thread (`edge/profile_ops.py`): convolutions are the time in both graphs, fp32 Conv 3.2031 ms (op_profile.json › graphs/detector.onnx/by_op_ms/Conv), pruned Conv 1.4015 ms (op_profile.json › graphs/detector_pruned_50.onnx/by_op_ms/Conv) plus FusedConv 0.5037 ms (op_profile.json › graphs/detector_pruned_50.onnx/by_op_ms/FusedConv). ORT pads the pruned channel counts when it optimises the graph (the first layer's 6 channels run as 8), so the kernels execute 106,937,856 (op_profile.json › graphs/detector_pruned_50.onnx/conv_macs_executed) MACs, not 101,795,328, against 217,497,600 (op_profile.json › graphs/detector.onnx/conv_macs_executed) for fp32. Padding is 5 % of the pruned work; the rest of the gap is throughput: about half the executed MACs take about 60 % of the convolution time (1.91 of 3.20 ms), so the narrow layers run about a sixth slower per MAC. Pruned + INT8 reaches 1.25 ms (prune_50.json › int8/latency_ms/onnxrt_1t), little under INT8 alone, for mAP 0.8411 (prune_50.json › int8/score/mAP). |

## Around the model: Python vs C++ (one process, 5 interleaved rounds)

INT8 static, 1 thread, median per image (`cpp/bench.py`):

- Python `onnx_predict`: model 1.222 ms (cpp_ort.json › python_ms_p50/model_ms), end to end 1.609 ms (cpp_ort.json › python_ms_p50/e2e_ms).
- C++ `cpp/detect_ort.cpp`: model 1.1583 ms (cpp_ort.json › cpp_ms_p50/model_ms), end to end 1.2601 ms (cpp_ort.json › cpp_ms_p50/e2e_ms), decode 0.0466 ms (cpp_ort.json › cpp_ms_p50/decode_ms).

So the model call costs the same from both languages; the Python limit is normalise + decode per
image. That wrapper decides the race with the classical pipeline: timed together on one thread,
classical 1.8029 ms (edge_vs_classical.json › ms_per_img/classical bgsub+ws/median) against INT8
end to end in Python 1.9444 ms (edge_vs_classical.json › ms_per_img/int8 end to end/median).
Timed per image in the same interleaved rounds (`cpp/bench.py --classical`, 3 runs, first run
cited), C++ end to end takes 1.5025 ms (cpp_ort_classical.json › cpp_ms_p50/e2e_ms) against
classical 1.5098 ms (cpp_ort_classical.json › classical_ms_p50/e2e_ms) and Python 1.7456 ms (cpp_ort_classical.json › python_ms_p50/e2e_ms):
in C++ the detector is under the classical pipeline in this and the five other runs (`_r2` to `_r6`,
6.0–7.5 % at low load; docs/RESULTS.md).

## The host

- Outside the kernels: session-run median minus kernel time is small, fp32 3.2716 ms (op_profile.json › graphs/detector.onnx/run_ms_median) vs 3.2317 ms (op_profile.json › graphs/detector.onnx/kernel_ms_mean), dynamic INT8 2.1408 ms (op_profile.json › graphs/detector_int8_dynamic.onnx/run_ms_median) vs 1.9087 ms (op_profile.json › graphs/detector_int8_dynamic.onnx/kernel_ms_mean): ORT's own overhead is not what separates the backends.
- Tail: p99 end to end 5.4061 ms (cpp_ort.json › cpp_ms_p99/e2e_ms) in C++ and 6.0375 ms (cpp_ort.json › python_ms_p99/e2e_ms) in Python, about 4x the median on both sides: set by the shared laptop, not by the code. Not a deployment number.
- Drift: the same INT8 graph on 1 thread measured 1.38 ms (quant_minmax.json › latency_ms/1t), 1.5649 ms (edge_vs_classical.json › ms_per_img/int8 model/median) and 1.222 ms (cpp_ort.json › python_ms_p50/model_ms) in three sessions.
